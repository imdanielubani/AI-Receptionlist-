# Platform research

One research pass per platform *version*. The snapshot gate (step 1) decides whether there is anything new to learn. If there isn't, stop.

## What this produces

Everything goes in `docs/platforms/`:

| File | Purpose |
|---|---|
| `<platform>.md` | Entry point, read at the start of every build. Covers access (MCP + REST), the build model, the default receptionist stack, top gotchas, account state, and links to the files below. Starts with `Last verified: YYYY-MM-DD`. |
| `<platform>/capabilities.md` | The capability map (step 3): every receptionist need, its status, and how to set it up. |
| `<platform>/setup-recipes.md` | Copy-paste API request bodies for each capability we use, checked against the spec (step 5). |
| `<platform>/custom-functions.md` | The gaps: what needs our own endpoint, and its contract (step 4). |
| `<platform>/changes.md` | Dated breaking changes and deprecations that affect us, newest first, each with the action to take. |
| `<platform>/sources.json` | Where the docs live. Used by the snapshot script. |
| `<platform>/snapshot/current/` | The accepted raw docs plus manifest. Generated by the script; never hand-edit it. |

## Step 1: The gate (decide whether to run)

1. **Sources.** If `docs/platforms/<platform>/sources.json` is missing, find the platform's docs and create it:
   ```json
   { "llms_txt": "...", "llms_full_txt": "... or null", "openapi": "... or null", "change_notices_prefix": "... or null" }
   ```
   - Try these on the docs host: `/llms.txt`, `/llms-full.txt`, `/openapi.yaml`, `/openapi.json`. Also look for spec links in `llms.txt` or on the API reference page.
   - `change_notices_prefix` is the URL prefix of the changelog or deprecation pages (Retell: `https://docs.retellai.com/deprecation-notice/`).
   - If there is no `llms.txt`, build one from `sitemap.xml`: a markdown list of `[Title](url)` links to the doc pages. Save it as `<platform>/snapshot/llms.txt` and point `llms_txt` at that file's URL or path.
2. **Snapshot.** Run `node scripts/docs-snapshot.mjs <platform>`. It fetches everything into `snapshot/incoming/`, splits the docs into `incoming/sections/<section>.md`, and prints a diff against `snapshot/current/` (also saved as `incoming/diff.json`).
3. **Act on the `verdict`:**

| Verdict | Do |
|---|---|
| `up-to-date` (and Last verified ≤ 90 days old) | Stop. Report "<Platform> docs unchanged since <date>; nothing to research." Delete `snapshot/incoming/`. |
| `stale` (nothing changed, but over 90 days) | Run step 6 only (live account check), bump `Last verified`, then accept. |
| `changed` | Triage (below), then run steps 2–8 only for what triage keeps. |
| `first-run` | Full research: steps 2–8 over everything. |

**Forced re-run.** The operator says the platform changed, or a build got an API error that contradicts our docs. Treat that as `changed` even if the snapshot is unchanged: the error is in our docs, so re-read the pages behind the failing feature.

**Triage for `changed`:**
- Every added or changed page under `change_notices_prefix` gets an entry in `changes.md`. Note the date, what breaks, the replacement, and the action.
- For every other changed page, diff the old and new text and decide whether it touches anything in the capability map. Cosmetic edits (typos, reworded examples, nav changes) need no research.
  ```bash
  page() { awk -v u="$2" 'prev ~ /^# / && $0=="Source: " u {on=1; print prev} on && /^Source: / && $0!="Source: " u {exit} on {print} {prev=$0}' "$1"; }
  d=docs/platforms/<platform>/snapshot
  diff <(page $d/current/llms-full.txt "<url>") <(page $d/incoming/llms-full.txt "<url>")
  ```
- Spec block changes (`path /x`, `schemas Name`): diff the YAML or JSON for that block, then update any recipe or capability row that uses it.
- Added or removed pages and endpoints usually mean a new feature or a retired one. Read them in full.
- Spec revisions bump often (Retell's changes daily), so a revision change on its own is not a reason to research.

## Step 2: Read the full docs

"Full" means every page is at least classified, and nothing in scope goes unread. The report's `sections` field shows page counts per section.

- **Read in full:** building agents, prompts and flows; tools and functions; call transfer; knowledge base; voices and languages; phone numbers, telephony and SIP; integrations; webhooks; testing and QA; deploy; reliability and limits; deprecations; pricing and billing.
- **Classify from title and first paragraph** (open a page only if it turns out to matter): account and team management, chat-only or SMS-agent features, outbound campaigns and batch calls, SDK internals, custom-LLM websockets, AI builder or assistant tools.
- **API reference:** the OpenAPI spec (`incoming/openapi.*`) is the source of truth for field names, enums, required fields and defaults. The reference pages add the prose.

**Fan out for big docs.** Retell's full docs are about 1.6 MB (~400k tokens), far more than one context should read.
- Spawn one subagent per large section, in parallel and in the background. Read small sections (< 60 KB) yourself.
- Give each subagent this prompt, filled in:

> Read `docs/platforms/<platform>/snapshot/incoming/sections/<section>.md` completely (use Read with offset/limit until the end; it has N pages). We are building AI phone receptionists on <Platform>. Return, with the source URL for every claim:
> 1. Every capability relevant to a receptionist, as rows of: `capability | status (Native / Integration / Custom function / Not possible / Unclear) | how it works | API endpoint + key fields | dashboard-only steps | cost | source URL`.
> 2. Anything a receptionist would need that this section shows the platform *can't* do natively.
> 3. Gotchas: defaults that are wrong for a receptionist, limits, region restrictions, and things that silently fail.
> 4. Deprecations or dated changes.
>
> Facts only, from the file. No guesses: mark anything unclear as Unclear.

- Merge the results yourself. Where subagents disagree, check the spec.

## Step 3: Map capabilities (`capabilities.md`)

Give every row below a status. Add rows for anything else the platform offers that a receptionist could use.

**Statuses:**
- **Native:** works with platform config alone.
- **Integration:** a built-in connector to a third party (note any dashboard-only connect step).
- **Custom function:** needs our own endpoint or code.
- **Not possible.**
- **Unclear:** say what's missing.

**Columns:** `Capability | Status | How | API setup (endpoint · key fields · MCP endpoint name) | Dashboard-only steps | Cost | Source`

**Checklist:**
- **Numbers and calls:**
  - buy a local number (which countries)
  - toll-free
  - import or port an existing number (SIP)
  - forward from the client's existing line
  - several numbers per agent
  - caller ID shown on transfers
  - concurrency limit and overflow/fallback
  - international callers
- **Conversation:**
  - greeting and who speaks first
  - voices (provider, cost, cloning)
  - languages and mid-call language switching
  - time zone and current date/time awareness for business hours
  - per-call dynamic variables (inbound webhook)
  - knowledge base (FAQ text, website crawl, files) and its limits
  - pronunciation and keyword boosting
  - interruption and silence handling
  - max call duration
  - spam and robocall handling
  - recording disclosure
- **Actions during the call:**
  - transfer: cold, warm, or chosen by time or reason
  - take a message
  - send an SMS
  - check availability
  - book, reschedule or cancel an appointment (which calendars)
  - look up the caller in a CRM
  - create a CRM record or ticket
  - emergency escalation (immediate transfer and alert)
  - end the call
  - press digits for an IVR
  - hand off to another agent
- **After the call:**
  - transcript, recording and summary
  - custom extracted fields
  - webhooks (events, retries, signature verification)
  - email or SMS notification to the owner
  - analytics
  - PII redaction and data retention
- **Testing:**
  - browser/web test call
  - text playground
  - simulated test cases and batch tests
  - QA scoring
  - latency metrics
  - test cost
- **Operations:**
  - versions, publish and rollback
  - staging vs production
  - keeping clients separate (workspaces, folders, tags)
  - API rate limits
  - per-client usage and billing
  - concurrency pricing

## Step 4: Flag custom functions (`custom-functions.md`)

Write one entry for every row marked **Custom function**, and for every **Integration** that only covers part of the need. Each entry has:

- **Need:** what the receptionist must do, and why native features fall short (with source).
- **When it runs:**
  - A **mid-call tool** has a latency budget under 3 s, and the agent speaks a filler line while it waits.
  - A **post-call webhook** has no latency pressure.
- **Contract:** the tool name, the input JSON Schema, the output fields the agent reads, and the error behaviour (what the agent says if it fails).
- **Platform wiring:** the tool type and the fields that point at our endpoint (timeout, retries, response variables).
- **Reuse:** whether this function is generic across clients (e.g. "email the owner a call summary") or client-specific. Generic functions get built once and shared.

## Step 5: Setup recipes (`setup-recipes.md`)

For each capability we'd use, give one titled section with:
- the REST method and path
- the MCP endpoint name
- a minimal request body
- a receptionist-tuned body with our defaults

**Minimum set:**
- create the brain (LLM, prompt or flow)
- create the agent
- update it and publish a version
- buy a number and bind it to the published version
- import a SIP number
- transfer tool
- SMS tool
- custom HTTP tool
- knowledge base: create and attach
- webhook setup and signature verification
- post-call extraction fields
- web test call, then fetch the call result

**Validation (required):**
- Every field name and enum value must exist in the snapshot's OpenAPI spec (grep it). When the MCP server is connected, also fetch the schema with its schema tool.
- Mark each recipe `validated against spec <revision>`.
- Never create billable resources during research: no phone numbers, calls, knowledge bases beyond the free tier, or voice clones.
- Free resources (LLMs, agents, flows) may be created only to prove a recipe works. Name them `zz-research-*` and delete them in the same run.

## Step 6: Live account check

Use harmless reads only (list agents, phone numbers, knowledge bases, connected integrations, voices) through the MCP server or REST. The key is in `.env`.
- Update the **Account state** section in `<platform>.md`: what exists, what's connected, and any limits shown.
- Flag anything that blocks receptionist builds, such as no integrations connected or no credits.

## Step 7: Save

1. Write or refresh all the output files.
   - Keep `<platform>.md` short. It is the entry point, so put the detail in the sub-files.
   - Set `Last verified:` to today in `<platform>.md` and in every file you touched.
2. **Check live clients.** For every change in `changes.md` with a future date, grep `clients/*/deploy.md` and `clients/*/receptionist/` for the affected features or fields. List the affected clients under that change.
3. If this is a new platform, update the Connected platforms table in `CLAUDE.md`.
4. Only after the docs are written, run `node scripts/docs-snapshot.mjs <platform> --accept`. Until then, the old snapshot stays the baseline, so an interrupted run loses nothing.

## Step 8: Report to the operator

Plain language, short:
- **Verdict:** first run, changed, stale, or unchanged. Give the snapshot date and spec revision.
- **Capability counts:** N native, N integration, N custom function, N not possible, N unclear. Add one line on the biggest gaps.
- **New custom functions** needed.
- **Breaking changes with dates,** and which live clients they affect.
- **What the operator must do on the dashboard,** if anything (e.g. connect Cal.com once).
